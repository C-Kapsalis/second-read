# Documentation and Diátaxis

Classify the page by the reader's need, not its title, after Diataxis: a **tutorial** teaches by doing one guaranteed path; a **how-to** guide gets a competent user to a goal; **reference** describes the machinery accurately and neutrally; an **explanation** gives context and reasons. Flag mode mixing: a tutorial that offers choices, a how-to that stops to teach theory, reference that gives advice, an explanation with steps to run.

Then check, quoting the line each time:

- **Prerequisites before use:** every file, key, environment variable, account or install a step needs is introduced before that step.
- **Steps run in order** as written, and each command can be copied and run (no prompt characters inside the command, placeholders marked as placeholders).
- **Examples agree with the reference:** flag names, parameters, defaults, ports and versions are the same in prose, code and tables.
- **Each procedure ends in an observable result** the reader can check.
- **A warning comes before anything destructive** or irreversible.
- **One term per thing,** descriptive link text, and headings that say what the section does.

 Verify prerequisites before usage, example-to-spec consistency, executable command results when authorized, complete links when checkable, and observable success. Separate product-source corroboration from an actually executed workflow. A README should help users find a successful starting path without becoming a copy of the entire docs site. An unfamiliar reader should know which page to visit and what they must supply next.

Sequence question: “At this exact step, have we already told the reader how to obtain the required file, key or environment variable?” If not, propose moving the prerequisite or inserting a precise, factual step; never invent a command or default.
